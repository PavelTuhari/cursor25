# Контур маркетинга в схеме UN4 (UNA.md)

Скрипты создают контур `YSEO_` внутри существующей схемы UNA. Порядок установки:

```
01_yseo_tables.sql     таблицы контура и настройки
02_yseo_views.sql      вьюшки VSEO_* (прикладной код обращается к ним)
03_pk_seo_util.sql     настройки, определение AI-сессии, лимит суммы для AI
04_pk_seo_doc.sql      жизненный цикл документов и маршрут согласования
05_pk_seo_budget.sql   план/факт и контроль лимитов бюджета
06_pk_seo_spend.sql    импорт расходов рекламы, регистрация публикаций
07_grants.sql          роли и права; пароль передаётся подстановкой &ai_bot_password
```

Запуск: `sqlplus UN4/<пароль>@<tns> @01_yseo_tables.sql` и далее по порядку.

## Что нужно проверить перед установкой

Скрипты написаны по опубликованному описанию структуры БД UNA
(<https://bsoft.gitbook.io/wiki/razrabotka/obekty-oracle/struktura-bazy-dannykh>).
Часть деталей в описании не раскрыта, поэтому следующие места **обязаны быть
сверены с командой UNA до первой установки** — они помечены здесь, а не
спрятаны в коде:

| Место | Предположение | Что проверить |
|---|---|---|
| `TMDB_DOCS_ADD` | Колонки `CAMP_CODE`, `RUN_ID`, `PLAYBOOK_SHA`, `NOTE` | Реальный состав таблицы. Если колонок нет — добавить их скриптом контура либо перенести эти поля в отдельную `YSEO_TMDB_DOCS_EXT` |
| `TMDB_DOCS_LOG` | Колонки `COD`, `USERID`, `DATAOPER`, `STATUS_FROM`, `STATUS_TO`, `NOTE` | Реальный состав. Формат записи истории движения документа |
| `TMDB_DOCS.COD` | Номер выдаётся как `MAX(COD)+1` | Есть ли штатная последовательность или пакет выдачи номеров. При конкурентной работе `MAX+1` недопустим |
| `DOCCOLOR` | 1 — жёлтый (черновик), 2 — серый (на согласовании), 3 — голубой (утверждён) | Фактическая кодировка цветов в системе |
| `UN$G$UTIL.TextIncrement` | Используется для нумерации `NRMANUAL` | Сигнатура и поведение на первом документе года |
| `TMS_SYSS ('S',3)` | Курс валюты лежит в `PRET`, код валюты в `DENUMIREA` | Фактическая раскладка раздела и наличие курса на дату |
| Проводки | Генерируются через `UN$GFC`, вызов в контуре пока не реализован | Сигнатура `UN$GFC` и настройка схем проводок (ТЗ ч. II §27) |
| Счета в `YSEO_TMS_SETUP` | 712 / 521 / 261 по общей логике НСБУ | Рабочий план счетов предприятия. Значения меняются `UPDATE`, без правки кода |
| `P$CHGLOG_MAKE_TRIGGER` | Принимает имя таблицы | Фактическая сигнатура процедуры |

Генерация проводок намеренно **не** реализована прямыми `INSERT` в `TMDB_CM`:
по соглашению UNA это делает `UN$GFC` по настройкам. Пока его интерфейс не
подтверждён, документы контура остаются непроведёнными — это осознанное
ограничение, а не пропуск.

## Инварианты, которые держит БД

Эти правила живут в пакетах, а не в приложении: ошибка в приложении не должна
приводить к бесконтрольным деньгам.

- AI-сессия не может согласовать, отклонить или аннулировать документ
  (`PK_SEO_UTIL.IS_AI_SESSION` → `MSG`).
- Автор документа не может быть его согласующим.
- Документ не проводится, пока не утверждён (`PK_SEO_DOC.ASSERT_APPROVED`).
- Удаления нет: только `ISVALID = 0` с сохранением истории в `TMDB_DOCS_LOG`.
- Повторный вызов с тем же `p_ext_id` возвращает существующий документ и не
  создаёт дубль.
- Сумма документа, создаваемого AI, ограничена настройкой `AI_MAX_DOC_SUMA`.
- Перерасход бюджета блокирует проведение (`ASSERT_LIMIT`), а уже понесённый
  расход рекламы помечается `IS_OVERBUDGET` и уходит в разбор.
