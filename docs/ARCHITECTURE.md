## Границы компонентов

Три границы держат систему разделяемой, и каждая выбрана осознанно.

**Приложение не знает про SFS.** Оно видит только `state` и `efactura_status`
как числа и сводит их в одно понятное покупателю слово. Новый код на стороне SFS
не ломает экран.

**UNA.md не подписывает и не говорит SOAP.** Учётная система отдаёт документ по
REST и получает статус. Сертификат, WS-Security и порядок элементов
DataContract — забота одного сервиса.

**Микросервис не пишет в ERP.** Он читает через три read-only вьюшки и хранит
всё своё в отдельной схеме. Обновление учётной системы не может его сломать, а
`DROP USER EFACTURA CASCADE` полностью снимает интеграцию.

## Мобильное приложение

Подробности — [mobile/docs/architecture.md](../mobile/docs/architecture.md).
Кратко, три принципа:

1. **Всё конфигурируется через JSON.** Бренд, тема, вкладки, экраны, блоки на
   экранах, тексты, сущности и правила синхронизации — в `config/*.json`. Тот же
   формат отдаёт сервер по `GET /app-config`, поэтому новая раскладка главной
   или новый клиент сети не требуют релиза в сторах.
2. **Offline-first на SQLite.** Схема БД **генерируется из конфигурации
   сущностей**; UI читает только из локальной базы.
3. **Синхронизация по API.** Дельта-загрузка по курсору `updated_at` и очередь
   исходящих изменений `_outbox` с экспоненциальными повторами.

Слои:

```
config/*.json ──▶ src/config    валидация, слияние удалённой конфигурации
                  src/db        драйверы SQLite, миграции, репозитории, outbox
                  src/api       HTTP-клиент: таймауты, повторы, refresh на 401
                  src/sync      движок pull/push
                  src/domain    цены, даты, штрихкоды, список покупок, компании
                  src/state     React-контексты и хуки данных
                  src/ui        блоки, компоненты, экраны, навигация
```

Экран — это список блоков в JSON. `BlockRenderer` сопоставляет строку `type`
компоненту через реестр `BLOCK_REGISTRY`; неизвестный тип в dev показывает
ошибку, в проде молча пропускается — так конфигурация с сервера не ломает
старую сборку.

## Микросервис e-Factura

Подробности — [efactura-service/README.md](../efactura-service/README.md).

```
config/ ──▶ src/config      загрузка, переопределение из окружения, валидация
            src/db          Oracle thin / in-memory, миграции, репозитории
            src/erp         чтение документов через вьюшки
            src/invoice     модель, XML по структуре гайда CTIF, валидация
            src/sign        XMLDSig: PKCS#12 или PKI-Server
            src/sfs         SOAP 1.1 + WS-Security, 19 типизированных операций
            src/queue       outbox: резерв серий, отправка, опрос статусов
            src/http        REST для UNA.md
mock/       эмулятор SFS с тем же контрактом
```

### Почему свой SOAP-клиент

Контракт фиксирован и мал: один binding, один namespace, простой
`UsernameToken` над TLS. WSDL-стек добавил бы зависимость, которую придётся
держать пропатченной у каждого клиента, и отобрал бы контроль над порядком
элементов — а WCF отклоняет тело, где порядок отличается. Свой писатель
(≈200 строк) с таблицей `FIELD_ORDER` предсказуем и покрыт тестами.

### Жизненный цикл документа

```
pending ─▶ reserved ─▶ built ─▶ [signed] ─▶ posted ─▶ confirmed
                                               │
                                               ├─▶ canceled  (отозван / отклонён)
   любой шаг при неустранимой ошибке ──────────┴─▶ failed
```

Каждый шаг фиксируется в базе **до** начала следующего. После падения сервис
продолжает с места остановки, а не отправляет фактуру заново: дубликат
фискальной фактуры — проблема для бухгалтерии, задержка — нет.

Различие устранимых и неустранимых ошибок:

| Неустранимая → `failed` сразу | Устранимая → повтор с backoff |
|---|---|
| документ не прошёл валидацию | таймаут, обрыв соединения |
| SOAP Fault (например, `AuthenticationFailedException`) | HTTP 429, 502, 503 |
| `Status = 3` в ответе операции | нет свободной серии в резерве |
| `ErrorMessage: 1 - XML incorect` | |

Отклонённый XML будет отклонён снова — тратить на него восемь попыток
бессмысленно.

## Данные в Oracle

**Схема сервиса** (`sql/001_schema.sql`):

| Таблица | Назначение |
|---|---|
| `EFACT_OUTBOX` | очередь документов, состояние, XML, подписанный XML, ошибки |
| `EFACT_SERIES` | серии и номера, зарезервированные в SFS заранее |
| `EFACT_TAXPAYER` | кэш реестра контрагентов |
| `EFACT_AUDIT` | каждый вызов SFS — для сверки с `GetLogs` |
| `EFACT_SCHEMA_VERSION` | применённые миграции |

`EFACT_OUTBOX` имеет уникальный ключ `(TENANT_ID, EXTERNAL_ID)` — повтор запроса
от вызывающей стороны идемпотентен, а не создаёт вторую фактуру.

Выборка очереди идёт с `FOR UPDATE SKIP LOCKED`, поэтому несколько экземпляров
сервиса на одной базе не возьмут один документ дважды.

**Контракт с ERP** (`sql/002_erp_views.sql`) — три вьюшки:
`V_EFACT_DOCUMENTS`, `V_EFACT_DOCUMENT_LINES`, `V_EFACT_PARTNERS`. Определения
переписываются под схему клиента, список колонок — нет.

## Мультиарендность

`service.tenantId` присутствует в каждой таблице сервиса. Один экземпляр может
обслуживать несколько клиентов сети на одной базе, но штатный сценарий —
отдельная установка на клиента: так проще разделить сертификаты и учётные данные
SFS, которые всё равно у каждого свои.
