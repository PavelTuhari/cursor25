# Безопасность

[← к оглавлению](INDEX.md)

## Границы доверия

```
   покупатель          UNA.md            una-efactura            SFS
       │                  │                    │                  │
   ────┼──── публично ────┼─── внутренний ─────┼─── гос. система ─┤
       │                  │      контур        │                  │
   токен сессии      Bearer сервиса      UsernameToken       фискальные
   в keychain        (apiToken)          над TLS             документы
                                         + сертификат
```

Каждый переход требует своих учётных данных, и ни один секрет не пересекает
границу дальше, чем нужно. Приложение никогда не видит ни пароля SFS, ни
сертификата; микросервис никогда не видит токена покупателя.

## Секреты и где они живут

| Секрет | Где хранится | Кто выдаёт |
|---|---|---|
| Токен сессии покупателя | keychain / keystore устройства (`expo-secure-store`) | бэкенд UNA.md |
| `service.apiToken` микросервиса | переменная окружения на сервере | администратор |
| Пароль API-пользователя SFS | переменная окружения / Vault | директор компании в кабинете e-Factura |
| Пароль Oracle | переменная окружения / Vault | DBA |
| Пароль PKCS#12 | переменная окружения / Vault | владелец сертификата |
| Файл `.p12` | файловая система, `chmod 400`, владелец — пользователь службы | УЦ |

**Ни один секрет не лежит в JSON-конфигурации и не попадает в образ.**
`config/service.config.json` содержит пустые строки на месте паролей; значения
приходят только из окружения. В OCI это Vault-секреты, инжектируемые как
переменные.

`.gitignore` микросервиса исключает `.env`, `certs/*.p12` и `certs/*.pfx`.

## Логи

Логгер вырезает значения ключей, совпадающих с
`password|passphrase|apikey|token|secret|authorization`, рекурсивно по вложенным
объектам. Реализация и тест — [`src/util/logger.ts`](../efactura-service/src/util/logger.ts).

Тела SOAP-запросов **не логируются** ни на каком уровне: в них и учётные данные,
и персональные данные контрагентов.

## Транспорт

Опубликованный binding SFS — `TransportWithMessageCredential`: пароль
защищён **только** TLS. Поэтому валидатор конфигурации отклоняет `http://` для
любого адреса, кроме `localhost` и `127.0.0.1`, где допустим локальный мок.
Проверка — в [`src/config/validate.ts`](../efactura-service/src/config/validate.ts),
тест на неё есть.

Исходящий трафик сервиса — ровно два адреса:

| Адрес | Зачем |
|---|---|
| `efactura-api.sfs.md:443` | API e-Factura |
| хост PKI-Server | только при `signing.mode: pkiserver` |

Всё остальное можно закрыть.

## Аутентификация REST-сервиса

Bearer-токен, сравнение **постоянного времени** (`timingSafeEqual`), чтобы по
времени ответа нельзя было подбирать токен посимвольно. `/health` открыт
намеренно — оркестратору не нужен секрет, чтобы узнать, жив ли процесс; ничего
чувствительного он не отдаёт.

Пустой `apiToken` отключает проверку. Это допустимо только в закрытом контуре и
явно печатается в лог при старте: `http.listening` с полем
`authenticated: false`.

## Права в базе

Пользователь `EFACTURA` получает:

```sql
GRANT CREATE SESSION, CREATE TABLE, CREATE SEQUENCE TO EFACTURA;
GRANT SELECT ON V_EFACT_DOCUMENTS      TO EFACTURA;
GRANT SELECT ON V_EFACT_DOCUMENT_LINES TO EFACTURA;
GRANT SELECT ON V_EFACT_PARTNERS       TO EFACTURA;
```

**Прав на запись в учётную систему нет и не запрашивается.** Сервис физически не
может испортить данные ERP — максимум прочитать их. Удаление интеграции —
`DROP USER EFACTURA CASCADE`, следов в ERP не остаётся.

## Изоляция процесса

Юнит systemd ограничивает сервис тем, что ему нужно:

* `NoNewPrivileges=true`
* `ProtectSystem=strict` — файловая система только на чтение, кроме `StateDirectory`
* `ProtectHome=true`
* `PrivateTmp=true`
* `ReadOnlyPaths=/etc/una-efactura`

В Docker процесс работает от непривилегированного пользователя `efactura`,
сертификат монтируется с хоста только на чтение и в образ не попадает.

## Персональные данные

**В приложении.** Профиль, чеки, карта лояльности и реквизиты компании лежат в
локальной SQLite. Выход из аккаунта удаляет с устройства всё, что относится к
аккаунту, вместе с их очередями; список покупок остаётся — это данные
устройства, а не аккаунта.

**В микросервисе.** `EFACT_OUTBOX` хранит XML фактур, а в них — наименования,
адреса и банковские реквизиты обеих сторон. `EFACT_TAXPAYER` кэширует реестр
контрагентов. Обе таблицы попадают под требования к обработке персональных
данных: включите их в политику хранения и в бэкап с тем же уровнем защиты, что и
учётная система.

## Подпись

Ключ не покидает процесс: PKCS#12 распаковывается один раз при старте, дальше
подписывает `node:crypto`. В режиме `pkiserver` ключ вообще не попадает к нам —
подпись считает HSM STISC, наружу уходят только байты `<SignedInfo>`.

Сервис проверяет срок действия сертификата при старте и предупреждает за 30
дней. Просроченный сертификат — это остановка всего потока фактур, а не
деградация.

## Что осталось за рамками

* **Ротация `apiToken`** делается вручную через перезапуск. Автоматической смены
  без простоя нет.
* **Аудит доступа к REST** ограничен строкой в логе на запрос; отдельной таблицы
  обращений нет.
* **Шифрование данных в покое** — на уровне Oracle (TDE), сервис своего слоя не
  добавляет.
