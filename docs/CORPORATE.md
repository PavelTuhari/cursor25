# Корпоративные клиенты и e-Factura

[← к оглавлению](INDEX.md)

Дополнительная опция поверх розничного приложения. Для обычного покупателя она
не существует: выключены флаги — нет ни пункта меню, ни экрана, ни сущностей в
базе.

## Зачем

Юридическому лицу чек не подходит: для вычета НДС и для учёта нужна **фискальная
фактура** (factura fiscală), зарегистрированная в SIA «e-Factura»
Государственной налоговой службы. Сегодня это делается вручную — покупатель
звонит в бухгалтерию сети, называет номер чека и ждёт. Опция превращает это в
одну кнопку в приложении.

## 1. Реквизиты компании

Сущность `company`, **двусторонняя**: покупатель заполняет её в приложении,
изменения уходят через очередь, поэтому форма работает без сети.

| Поле | Обязательно | Проверка |
|---|---|---|
| `idno` | да | ровно 13 цифр (IDNO юрлица или IDNP физлица) |
| `name` | да | не короче 2 символов |
| `legal_address` | да | не короче 5 символов — попадает в фактуру |
| `vat_code` | нет | 6–8 цифр; компания ниже порога не зарегистрирована как плательщик |
| `bank_account` | нет | `MD` + 2 контрольные цифры + 20 символов |
| `contact_email` | нет | обычная проверка адреса |
| `delivery_address`, `bank_name`, `bank_swift`, `contact_name`, `contact_phone` | нет | |

Правила — в [`src/domain/company.ts`](../mobile/src/domain/company.ts), функция
`validateCompany`. Она возвращает **ключи переводов**, а не тексты, поэтому
сообщения об ошибках существуют во всех трёх локалях; тест это проверяет.

**Подстановка из реестра.** По IDNO приложение запрашивает название и адрес из
реестра SFS, чтобы покупателю не пришлось перепечатывать их с сертификата.

**Признаки, которые ставит сервер, а не приложение:**

* `efactura_verified` — компания найдена в фискальном реестре;
* `efactura_actor` — компания зарегистрирована в системе e-Factura.

Оба берутся из ответа `GetTaxpayersInfo`. Приложение показывает их значками и
никогда не изменяет — иначе клиент мог бы «подтвердить» себя сам.

## 2. Запрос фактуры по чеку

Блок `invoice_request` на экране чека. Доступен, когда:

* покупатель авторизован;
* реквизиты компании заполнены;
* по этому чеку ещё не запрашивали фактуру;
* не истёк `corporate.requestWindowDays` (по умолчанию 30 дней).

Нажатие пишет локальную запись с `id = "req-<receipt_id>"` и ставит её в
очередь. Идентификатор выводится из чека, поэтому **повторное нажатие не создаёт
вторую заявку** — ни при двойном тапе, ни при повторе после обрыва сети.

Единственное исключение: заявка в состоянии `failed` не блокирует новую. Ошибка
на нашей стороне не должна оставлять покупателя без фактуры.

## 3. Обработка в микросервисе

`POST /efactura/v1/invoices` принимает документ и **проверяет его синхронно**:
арифметику каждой строки, соответствие итогов сумме строк, форматы IDNO,
различие поставщика и покупателя. Ошибка — `422` со списком конкретных полей.

Проверка здесь, а не в фоне, потому что `PostInvoices` отвечает на кривую пачку
одним «1 - XML incorect» без указания документа и поля. Всё, что можно поймать
самим, экономит обращение в поддержку CTIF.

Дальше очередь: резерв серии и номера → XML по структуре гайда → подпись (если
настроена) → `PostInvoices` → опрос `CheckInvoicesStatus` до терминального
статуса.

## 4. Что видит покупатель

Приложение сводит два поля — `state` очереди сервиса и `efactura_status` из
SFS — в одно слово:

| Показывается | Когда |
|---|---|
| **Запрошена** | заявка в очереди, статуса из SFS ещё нет, или статус 0 (черновик) |
| **Выписана** | статус 1 (подписана поставщиком) или 7 (отправлена покупателю) |
| **Подписана** | статус 3 (принята покупателем) или 8 (подписана покупателем) |
| **Доставлена** | статус 10 |
| **Отклонена** | статус 2 (отклонена покупателем) или 5 (отозвана поставщиком) |
| **Ошибка** | `state = failed` — приоритетнее любого статуса |

Маппинг — `invoiceView` в [`src/domain/company.ts`](../mobile/src/domain/company.ts).
Неизвестный код попадает в «Запрошена», а не роняет экран: если SFS введёт новый
статус, приложение переживёт это до обновления маппинга.

Для выписанной фактуры доступны **PDF** (печатная форма из
`GetInvoicesContentForPrint`) и **QR-код** со ссылкой на документ в кабинете
e-Factura.

## Конфигурация

Секция `corporate` в
[`app.config.json`](../mobile/config/app.config.json):

| Ключ | Смысл |
|---|---|
| `enabled` | главный выключатель опции |
| `requireVerification` | считать компанию рабочей только после проверки в SFS |
| `companyEndpoint`, `invoicesEndpoint`, `taxpayerLookupEndpoint` | адреса на бэкенде UNA.md |
| `editableFields` | какие поля реквизитов покупатель может править |
| `requestFromReceipt` | показывать кнопку запроса на чеке |
| `requestWindowDays` | сколько дней после покупки можно просить фактуру |
| `efactura.portalUrl` | ссылка на кабинет |
| `efactura.showStatus`, `showQr`, `allowPdfDownload` | что показывать в списке |

Плюс два фич-флага: `features.corporate` и `features.eFactura`. Первый включает
кабинет и реквизиты, второй — фактуры. Их можно разводить: сеть может собирать
реквизиты юрлиц раньше, чем запустит фискальные фактуры.
