### Корпоративная опция

Разделено на то, что проверяет **правила**, и то, что проверяет **конфигурацию** —
второе ловит рассинхрон между JSON и кодом, который типы поймать не могут.

**Правила** ([`src/domain/company.ts`](../mobile/src/domain/company.ts)):

* IDNO ровно 13 цифр; пробелы и дефисы из вставленного текста игнорируются;
* код НДС необязателен, но проверяется, если указан;
* IBAN `MD` + 22 символа, регистр не важен;
* полный маппинг восьми кодов `efactura_status` в шесть состояний покупателя;
* `failed` приоритетнее любого статуса SFS;
* одна заявка на чек — **но после `failed` можно снова**, иначе наша ошибка
  оставила бы покупателя без фактуры;
* `EAA 000005948`, либо тире, пока серия не назначена.

**Конфигурация:**

* фич-флаги и секция `corporate` на месте;
* сущности `company` и `fiscal_invoices` объявлены, у `fiscal_invoices` есть все
  колонки, которые читает экран, — потеря одной сломала бы экран молча;
* экран `corporate.json` ссылается только на зарегистрированные типы блоков;
* пункт меню в профиле ведёт на `corporate` и виден только авторизованным;
* каждый ключ перевода, который может вернуть валидатор компании, существует во
  **всех трёх локалях**.

### Что здесь стоит отметить

**Порядок элементов DataContract.** WCF отклоняет тело, где порядок отличается
от объявленного. Тест берёт сгенерированный envelope и сравнивает
последовательность тегов с таблицей `FIELD_ORDER` — это единственная защита от
регрессии, которую невозможно заметить локально: ошибка проявилась бы только на
продакшене SFS.

**Подпись проверяется криптографически.** Тест генерирует пару ключей и
самоподписанный сертификат через node-forge, упаковывает в PKCS#12, подписывает
документ и затем **верифицирует подпись публичным ключом** через
`crypto.createVerify`. То есть проверяется не «в XML появился тег
`<SignatureValue>`», а что подпись математически верна над теми байтами, над
которыми должна быть.

**Подписи стекаются.** Второй вызов добавляет `<SignatureContent>` внутрь
существующего `<Signatures>`, не создавая второй обёртки, и **не трогает
`<SupplierInfo>`** — отдельный тест сравнивает эту часть до и после подписания.
Так подпись покупателя ложится поверх подписи поставщика.

**Сквозной сценарий идёт через настоящий HTTP.** Мок SFS поднимается на
случайном порту, сервис ходит в него `fetch`. Проверяется весь путь: резерв
серий → XML → envelope → разбор ответа → опрос статусов → аудит. Мок отклоняет
вызов без `UsernameToken`, поэтому есть тест, что неверные учётные данные дают
понятный fault, а не пустой результат.

**Ошибки разделены по типу.** Отдельные тесты на то, что невалидный документ
уходит в `failed` **с первой попытки**, а таймаут — повторяется. Неверное
поведение здесь стоит дорого: либо восемь бессмысленных попыток отправить кривой
XML, либо потерянная фактура из-за моргнувшей сети.

## Превью-окно кошелька

Экраны автотестами не покрыты, поэтому кошелёк проверяется вживую через
внутреннее окно: `?preview=wallet&scenario=...`, пять состояний, каждое по
своему URL. Подробности — [DEVELOPMENT.md](DEVELOPMENT.md#превью-окна).

Оно окупилось сразу: первый же прогон нашёл четыре ошибки, которых не видели ни
типы, ни валидатор конфигурации, ни 154 теста.

| Что нашлось | Почему это не ловилось иначе |
|---|---|
| Экраны `wallet`, `connections`, `corporate` и `receipts` **не входили в бандл** | `validate-config` читает файлы с диска, а не список в `defaults.ts`; на устройстве без сети экран показывал бы «не настроен» |
| Пустое состояние выводилось **дважды** | каждый блок по отдельности вёл себя правильно |
| На исходящей фактуре стояло «От MAGAZIN DEMO SRL» — то есть от нас самих | текст брался из одного поля для обоих направлений |
| Отклонённая фактура попадала в «К оплате» | арифметика верна, ошибка в том, *что* считать обязательством |

Первую из них закрыл новый тест
[`bundled-config.test.ts`](../mobile/__tests__/bundled-config.test.ts): он
сверяет список в `defaults.ts` с содержимым `config/screens/`. Четвёртую —
тест на `summarise`. Вторая и третья остаются проверяемыми глазами: это ровно
тот класс ошибок, ради которого окно и сделано.

## Чего тесты не покрывают

Честный список — важнее, чем цифра покрытия.

| Не покрыто | Почему и что делать |
|---|---|
| **Настоящий SFS** | доступа к песочнице нет; см. [ROADMAP.md](ROADMAP.md#открытые-вопросы) |
| **Вход хеша перед подписью** | гайд не описывает, какие байты идут в `<hash>` — подтвердить на песочнице |
| **Настоящий Oracle** | репозитории покрыты через in-memory реализацию того же интерфейса; SQL не выполнялся против базы |
| **STISC PKI-Server** | формат обмена не опубликован; вызов сведён в одну функцию `requestSignature()` |
| **Рендеринг экранов приложения** | компонентных тестов нет. Кошелёк проверяется превью-окном (см. выше); корпоративный экран и форма подключения — пока только типами и правилами |
| **Форма редактирования реквизитов** | ещё не написана |
