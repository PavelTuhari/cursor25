# Сценарий тестирования: officeplus.md → НН → кошелёк → SFS

[← к оглавлению](INDEX.md) · Редакция 1.0 · 25.08.2026

Полный цикл: покупатель оформляет заказ в интернет-магазине на платформе
UNA.md, получает налоговую накладную, видит её в универсальном приложении рядом
с накладными от поставщиков вне платформы и закрывает документ, не заходя в
кабинет e-Factura.

Сценарий проверяет **всю цепочку целиком** — то, что каждый компонент работает
по отдельности, проверяется юнит-тестами и здесь не дублируется.

## 1. Стенды

| Контур | Назначение | SFS |
|---|---|---|
| **LOCAL** | разработка, CI | эмулятор `mock/sfs-mock.ts` |
| **TEST** | приёмка | тестовая среда SFS (запрашивается в CTIF, 022 822222) |
| **PROD** | боевой | `efactura-api.sfs.md` |

Полный прогон обязателен на LOCAL перед каждым релизом и на TEST перед выходом
в PROD. На PROD выполняется только дымовой набор — §8.

## 2. Действующие компании

| Роль | Компания | IDNO | Где заведена |
|---|---|---|---|
| Продавец на платформе | MAGAZIN DEMO SRL | `1000000000033` | UNA.md, микросервис, связка `actorRole 1` |
| Покупатель | ALFA DEMO SRL | `1000000000015` | приложение, связка `actorRole 2` |
| Сторонний поставщик | BETA DEMO SRL | `1000000000024` | **только в SFS**, вне платформы |

Третья компания — ключевая для сценария: она проверяет, что кабинет
действительно «все НН от всех», а не только от продавцов UNA.md.

## 3. Учётные записи

| Что | Значение на LOCAL |
|---|---|
| Пользователь приложения | телефон `+37360000001`, код `1234` |
| API-пользователь продавца | `supplier` / `supplier` |
| API-пользователь покупателя | `buyer` / `buyer` |
| Заведомо неверный пароль | `buyer` / `wrong` — для ветки TC-09 |

## 4. Предусловия

1. Стенд поднят: эмулятор SFS, микросервис, mock API, приложение.
2. Схема микросервиса мигрирована, `EFACT_CONNECTION` и `EFACT_INBOX` пусты.
3. Локальная база приложения очищена (переустановка или сброс данных).
4. У покупателя нет ни одной привязанной компании.
5. В эмуляторе SFS **заранее** заведена одна НН от стороннего поставщика
   BETA DEMO на покупателя — она не проходила через наш микросервис.

Последний пункт важен: если завести её через нашу же выписку, сценарий проверит
не то, что нужно.

# 5. Основной путь

## TC-01 · Заказ на officeplus.md

| № | Действие | Ожидаемо |
|---|---|---|
| 1.1 | Открыть officeplus.md, войти под покупателем | В аккаунте видны реквизиты компании: IDNO `1000000000015`, код НДС |
| 1.2 | Положить в корзину 3 позиции, оформить заказ | Заказ создан, номер вида `ORD-2026-0815` |
| 1.3 | Оплатить | Статус «оплачен» |
| 1.4 | Проверить корзину покупателя | Признак «Юридическое лицо» проставлен автоматически, не выбирался вручную |

**Проверить в базе UNA.md:** заказ содержит `buyer_idno`, совпадающий с
компанией аккаунта.

## TC-02 · Выписка НН продавцом

| № | Действие | Ожидаемо |
|---|---|---|
| 2.1 | Дождаться выписки либо `POST /efactura/v1/tick` | Документ в очереди появился |
| 2.2 | `GET /efactura/v1/invoices/ORD-2026-0815` | `state: posted`, серия и номер назначены |
| 2.3 | Проверить `externalId` | Равен номеру заказа — не сгенерирован отдельно |
| 2.4 | `GET .../xml` | `<Buyer IDNO="1000000000015">`, суммы совпадают с заказом |
| 2.5 | Повторить шаг 2.1 ещё дважды | **Вторая НН не создана** — идемпотентность по номеру заказа |

Шаг 2.5 — не формальность: повторный вебхук от платёжного шлюза в проде
случается регулярно.

## TC-03 · Привязка компании покупателем

| № | Действие | Ожидаемо |
|---|---|---|
| 3.1 | В приложении: Кошелёк → Подключить компанию | Открывается форма ввода IDNO |
| 3.2 | Ввести `1000000000015` | Подставлены название, адрес, код НДС из реестра SFS; показан признак «Зарегистрирован в e-Factura» |
| 3.3 | Ввести API-пользователя `buyer` / `buyer` | Показан экран согласия с текстом: что читаем, как часто, как отозвать |
| 3.4 | Отклонить согласие | Связка **не создана**, пароль не отправлен |
| 3.5 | Повторить и принять согласие | Связка создана, статус «Проверяется» → «Активна» |
| 3.6 | `GET /efactura/v1/connections` | Связка есть; **пароля в ответе нет ни в каком виде** |
| 3.7 | Проверить локальную базу устройства | Пароля нет ни в одной таблице, ни в очереди |

Шаги 3.6 и 3.7 — контроль FR-4 и SEC-2. Проверять именно грепом по файлу базы,
а не глазами по экрану.

## TC-04 · Загрузка входящих

| № | Действие | Ожидаемо |
|---|---|---|
| 4.1 | Дождаться первого опроса или вызвать его принудительно | В кошельке появились НН |
| 4.2 | Найти НН от MAGAZIN DEMO | Есть, статус «Ожидает решения» |
| 4.3 | Найти НН от BETA DEMO | **Есть** — документ пришёл из SFS, через платформу он не проходил |
| 4.4 | Сверить суммы НН от MAGAZIN DEMO с заказом | Совпадают до копейки |
| 4.5 | Открыть PDF | Печатная форма открывается |
| 4.6 | Открыть QR-код | Ведёт на документ в кабинете e-Factura |

Шаг 4.3 — главная проверка всего сценария. Если сюда попала только НН от
платформы, кабинет не выполняет своё назначение.

## TC-05 · Отсутствие дублей

| № | Действие | Ожидаемо |
|---|---|---|
| 5.1 | Подсчитать НН от MAGAZIN DEMO за серию и номер из TC-02 | Ровно **одна** запись |
| 5.2 | Запустить опрос SFS ещё дважды | По-прежнему одна |
| 5.3 | `SELECT COUNT(*) FROM EFACT_INBOX WHERE SERIA=… AND NUMBER_=…` | `1` |

Документ приходит двумя путями — напрямую от продавца и из SFS. Склейка по
`supplier_idno + seria + number` (FR-11).

## TC-06 · Приём документа

| № | Действие | Ожидаемо |
|---|---|---|
| 6.1 | Открыть НН от MAGAZIN DEMO, нажать «Принять» | Статус «Отправляется» |
| 6.2 | Дождаться подтверждения | Статус «Принята» |
| 6.3 | Проверить в кабинете e-Factura покупателя | Статус документа — «принята покупателем» (код 3) |
| 6.4 | Проверить `EFACT_AUDIT` | Есть запись `PostAcceptedInvoices` с `CONNECTION_ID` |
| 6.5 | Попробовать принять повторно | Кнопка недоступна, повторный вызов в SFS не уходит |

## TC-07 · Отклонение документа

| № | Действие | Ожидаемо |
|---|---|---|
| 7.1 | Открыть НН от BETA DEMO, нажать «Отклонить» | Требуется комментарий |
| 7.2 | Отправить с пустым комментарием | Отклонено формой, вызов не уходит |
| 7.3 | Ввести «Расхождение по количеству», отправить | Статус «Отклонена» |
| 7.4 | Проверить в кабинете e-Factura | Код 2, комментарий виден поставщику |

## TC-08 · Оплата (этап 3)

| № | Действие | Ожидаемо |
|---|---|---|
| 8.1 | Открыть принятую НН, нажать «Оплатить» | Сумма, получатель и назначение подставлены из документа |
| 8.2 | Подтвердить оплату | Платёж прошёл, НН помечена «Оплачена» |
| 8.3 | Проверить статус в SFS | **Не изменился** — оплата фискального статуса не касается |
| 8.4 | Оплатить частично | Показан остаток, статус «Оплачена частично» |

Шаг 8.3 фиксирует FR-24: две системы, и путать их нельзя.

# 6. Ветки отказов

## TC-09 · Неверный пароль связки

Привязать компанию с паролем `wrong`. Ожидается: связка переходит в
«Недействительна» **после первой же попытки**, повторов нет, пользователю
показано, что делать. Опрос по этой связке прекращается.

## TC-10 · Работа офлайн

1. Включить самолётный режим.
2. Открыть кошелёк — **все ранее загруженные НН и PDF доступны**.
3. Принять документ — статус «Отправляется».
4. Выключить самолётный режим.
5. Действие уходит в SFS, статус становится «Принята».

Проверяет FR-15 и FR-17 разом.

## TC-11 · SFS недоступна

Остановить эмулятор SFS. Ожидается: приложение работает на локальных данных,
опрос повторяется с нарастающей паузой, связка **не** переводится в
«Недействительна» — недоступность сервиса не то же самое, что неверный пароль.
После запуска эмулятора опрос возобновляется сам.

## TC-12 · Отзыв доступа

| № | Действие | Ожидаемо |
|---|---|---|
| 12.1 | Отозвать доступ к компании | Запрошено подтверждение и выбор: удалять ли загруженные НН |
| 12.2 | Подтвердить с сохранением документов | Связка удалена, НН остались, опрос прекратился |
| 12.3 | `SELECT SFS_USERNAME, SFS_SECRET FROM EFACT_CONNECTION` | Строки **нет** — не флаг, а физическое удаление |
| 12.4 | Дождаться следующего цикла опроса | Обращений к SFS от этой компании нет |

## TC-13 · Права внутри компании

Пользователь с правом «только просмотр»: список и PDF видит, кнопки «Принять»,
«Отклонить» и «Оплатить» недоступны, прямой вызов REST возвращает `403`.

Проверять именно вызовом REST в обход интерфейса — скрытая кнопка не есть
ограничение права.

## TC-14 · Некорректный документ от продавца

Выписать НН с нарушенной арифметикой строки. Ожидается: `422` со списком
конкретных полей, документ **не** попадает в очередь, в SFS ничего не уходит.

# 7. Что проверяется на каждом слое

| Слой | Чем проверять |
|---|---|
| Интерфейс | вручную по шагам выше |
| REST микросервиса | `curl` либо автотест `__tests__/e2e-wallet.test.ts` |
| База микросервиса | SQL-запросы из шагов TC-05, TC-12 |
| База устройства | греп по файлу SQLite — TC-03.7 |
| SFS | кабинет e-Factura на TEST; на LOCAL — состояние эмулятора |
| Аудит | `EFACT_AUDIT` и экран истории обращений в приложении |

## Автоматизация

**Автоматизируется целиком:** TC-02, TC-04, TC-05, TC-09, TC-11, TC-14 —
серверная часть, гоняется в CI против эмулятора.

**Автоматизируется частично:** TC-06, TC-07, TC-12 — REST автоматически,
подтверждение в кабинете e-Factura вручную.

**Только вручную:** TC-01, TC-03, TC-10, TC-13 — интерфейс, согласие,
самолётный режим, права.

# 8. Дымовой набор для PROD

На боевом контуре выполняется минимум, не создающий лишних фискальных
документов:

1. `GET /efactura/v1/health` и `/ready` — отвечают.
2. `GET /efactura/v1/taxpayers/{idno}` — реальный вызов SFS, проверяет сеть,
   TLS, учётные данные и разбор ответа разом.
3. Привязка одной тестовой компании и загрузка входящих **без действий** над
   ними.
4. Отзыв доступа.

Выписка и приём на PROD выполняются только по согласованию с бухгалтерией: это
настоящие фискальные документы, и отменять их придётся тоже по-настоящему.

# 9. Критерии приёмки

Сценарий считается пройденным, когда:

1. TC-01 … TC-07 проходят на LOCAL и на TEST.
2. TC-09 … TC-14 проходят на LOCAL.
3. TC-08 — после этапа 3 и решения по OQ-5.
4. В кошельке видны НН **обоих** поставщиков — и с платформы, и стороннего.
5. Ни в одном ответе REST, ни в одном логе и ни в одной таблице устройства нет
   пароля API-пользователя.
6. Дубль НН не воспроизводится при десяти циклах опроса подряд.
